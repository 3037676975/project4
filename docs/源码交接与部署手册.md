更新日期：2026-09-05  
适用分支：`main`  
仓库：`3037676975/project4`

> 本手册以当前 GitHub `main` 分支为唯一交付基准。旧的 `KnowFlow-v24-full-source.zip` 已从仓库删除，不再把历史 ZIP 当作部署源，避免 ZIP、GitHub 和服务器三份代码互相漂移。

## 1. 当前项目是什么

Project4 / KnowFlow 是一套面向企业场景的 AI 客服与知识库 SaaS，当前主链路为：

```text
企业资料
  ↓
文本解析 / PaddleOCR
  ↓
文本切片
  ↓
Embedding
  ↓
Qdrant
  ↓
Rerank
  ↓
DeepSeek 生成
  ↓
官网客服 / 企业工作台 / API / 人工客服兜底
```

当前私有化版本已经把 OCR 调整为 **服务器本地 PaddleOCR**，企业上传图片、扫描 PDF 以及 Office 文档时，默认不再依赖腾讯云或百度云 OCR 计费接口。

---

## 2. 当前私有化服务架构

`docker-compose.private.yml` 是当前服务器部署的主 Compose 文件。

默认服务：

| 服务 | 作用 | 容器端口 | 宿主机暴露 |
|---|---|---:|---|
| `knowflow` | Next.js / Worker 主应用、API、后台、RAG 编排 | 3000 | `127.0.0.1:3000` |
| `qdrant` | 向量数据库 | 6333 | `127.0.0.1:6333` |
| `paddleocr` | 本地免费 OCR + Office 转 Markdown | 8002 | `127.0.0.1:8002` |
| `email-relay` | SMTP 邮件中继 | 8025 | 仅 Docker 内网 |
| `operations-sweeper` | 后台运营清理/巡检任务 | - | 不暴露 |

可选服务：

| 服务 | 作用 | 启动方式 |
|---|---|---|
| `document-parser` | Docling + RapidOCR 兼容文档解析 | `--profile parser` |

默认拓扑：

```text
浏览器
  ↓
宝塔 / Nginx / 公网端口 28441
  ↓
127.0.0.1:3000
  ↓
KnowFlow
  ├── PaddleOCR :8002
  ├── Qdrant :6333
  ├── Email Relay :8025
  ├── DeepSeek API
  ├── SiliconFlow Embedding / Rerank
  └── 支付 / SMTP 等第三方接口
```

OCR、Qdrant 和应用端口都只绑定 `127.0.0.1`，不要直接把 6333、8002 暴露到公网。

## 3. PaddleOCR 当前实现

### 3.1 默认模型

当前本地 OCR 使用：

```text
PaddleOCR 3.7.x
PaddlePaddle 3.3.x
PP-OCRv6
PP-OCRv6_small_det
PP-OCRv6_small_rec
CPU 模式
MAX_CONCURRENCY=1
```

服务目录：

```text
services/paddleocr/
├── Dockerfile
├── requirements.txt
├── README.md
└── app/
    ├── __init__.py
    └── main.py
```

### 3.2 支持范围

本地服务当前支持：

- PNG / JPG / JPEG / BMP / WEBP / TIFF 图片 OCR；
- 扫描 PDF OCR；
- DOCX / XLSX / PPTX 等新版 Office 文档转 Markdown；
- OCR 健康检查；
- 服务启动时真实执行一次推理自检，避免“接口显示健康但模型实际不能运行”。

企业知识库默认路由：

```text
KnowFlow -> paddleocr:8002 -> PaddleOCR -> 文本 -> Embedding -> Qdrant
```

### 3.3 为什么保留 `PARSER_API_KEY`

`paddleocr` 与 `knowflow` 之间使用 Bearer Token 鉴权，复用 `.env.private` 中的 `PARSER_API_KEY`。

这样即使 OCR 端口以后被误开放，也不会变成完全无鉴权接口。

### 3.4 云 OCR 状态

旧腾讯云 / 百度云 OCR 调用逻辑已经退出主业务链路。当前私有化部署的企业文档默认只走服务器本地 PaddleOCR。

如果未来确实要重新接云 OCR，应作为单独的可选 Provider 实现，不要直接修改本地 OCR 主链路。

## 6. 服务器推荐配置

当前带 PaddleOCR + Qdrant 的单机私有化部署建议：

```text
CPU：4 核以上，8 核更舒适
内存：8 GB 推荐
磁盘：30 GB 起，建议 50 GB 以上
Docker：24+
Docker Compose：v2
系统：OpenCloudOS / Rocky / Ubuntu 等主流 Linux
```

PaddleOCR 第一次构建/启动会下载模型，第一次部署会比普通 Next.js 项目明显更慢。

不要因为首次下载模型需要几分钟就重复执行多次部署，否则可能同时触发多个 Docker 构建，反而更慢。

## 7. 首次私有化部署

服务器项目目录建议保持：

```text
/www/wwwroot/project4
```

进入目录：

```bash
cd /www/wwwroot/project4
```

首次执行：

```bash
bash scripts/init-private.sh
```

脚本会创建：

```text
.env.private
```

其中保存：

- 配置加密密钥；
- 本地超级管理员密码；
- 本地登录 Session Secret；
- PaddleOCR / Parser 内部 Token；
- Qdrant Token；
- 支付回调 Secret；
- 后台任务 Secret；
- Mail Relay Token；
- SMTP 配置。

`.env.private` **不能提交 GitHub，也不要删除。**

## 8. 当前 `.env.private` 重点参数

最重要的部分：

```dotenv
APP_BASE_URL=http://你的公网域名或IP:端口
LOCAL_OCR_MODE=paddleocr
PARSER_API_KEY=随机长Token

OCR_MODEL_VERSION=PP-OCRv6
OCR_DET_MODEL=PP-OCRv6_small_det
OCR_REC_MODEL=PP-OCRv6_small_rec
OCR_MAX_CONCURRENCY=1
OCR_MAX_FILE_BYTES=12582912
OCR_OMP_NUM_THREADS=4
OCR_MKL_NUM_THREADS=4

QDRANT_COLLECTION=knowflow_chunks
QDRANT_VECTOR_SIZE=1024
```

当前服务器可以使用：

```dotenv
APP_BASE_URL=http://186.244.245.177:28441
```

以后绑定正式域名后，建议改为：

```dotenv
APP_BASE_URL=https://你的域名
```

并由宝塔 Nginx 配置 HTTPS。

## 9. Docker Compose 常用命令

所有命令都在项目根目录执行：

```bash
cd /www/wwwroot/project4
```

查看状态：

```bash
docker compose --env-file .env.private -f docker-compose.private.yml ps
```

启动：

```bash
docker compose --env-file .env.private -f docker-compose.private.yml up -d
```

重新构建并启动：

```bash
docker compose --env-file .env.private -f docker-compose.private.yml up -d --build
```

查看主应用日志：

```bash
docker compose --env-file .env.private -f docker-compose.private.yml logs -f --tail=200 knowflow
```

查看 PaddleOCR 日志：

```bash
docker compose --env-file .env.private -f docker-compose.private.yml logs -f --tail=200 paddleocr
```

查看 Qdrant 日志：

```bash
docker compose --env-file .env.private -f docker-compose.private.yml logs -f --tail=200 qdrant
```

只重启 OCR：

```bash
docker compose --env-file .env.private -f docker-compose.private.yml restart paddleocr
```

停止整个项目：

```bash
docker compose --env-file .env.private -f docker-compose.private.yml down
```

不要随便加 `-v`：

```bash
# 不建议随便执行
docker compose down -v
```

因为 `-v` 会删除项目持久化 Volume。

```json

  "device": "cpu",
```


## 11. 宝塔 + GitHub 自动部署

当前推荐发布方式：

```text
GitHub main
  ↓
宝塔 Git 自动部署 / Webhook
  ↓
scripts/auto-deploy.sh
  ↓
拉取 main
  ↓
构建 knowflow + paddleocr
  ↓
docker compose up -d --force-recreate
  ↓
127.0.0.1:3000 健康检查
```

服务器不要再手工维护一份“改过但没提交 GitHub”的正式代码。

正确原则：

```text
GitHub main = 唯一源码真相
服务器 = 运行副本
.env.private = 服务器私密配置
Docker Volume = 服务器业务状态
```

如果宝塔插件触发脚本，部署命令建议直接使用：

```bash
cd /www/wwwroot/project4 && bash scripts/auto-deploy.sh
```

## 19. 常见故障

### 19.1 Git 报 dubious ownership

```bash
git config --global --add safe.directory /www/wwwroot/project4
```

### 19.2 PaddleOCR 构建很慢

先确认只有一个构建进程：

```bash
docker ps
docker compose --env-file .env.private -f docker-compose.private.yml ps
```

首次下载 PaddlePaddle wheel 和模型本来就会较慢。

### 19.3 OCR 容器启动失败

```bash
docker compose --env-file .env.private -f docker-compose.private.yml logs --tail=300 paddleocr
```

重点检查：

- 内存是否不足；
- 模型是否下载失败；
- Python 包是否安装失败；
- `PARSER_API_KEY` 是否存在；
- Docker DNS 是否正常。

### 19.4 Qdrant 不健康

```bash
docker compose --env-file .env.private -f docker-compose.private.yml logs --tail=200 qdrant
```

不要直接删除 `qdrant-data`。

### 19.5 主站启动但 OCR 不工作

检查：

```bash
grep '^LOCAL_OCR_MODE=' .env.private
grep '^PARSER_API_KEY=' .env.private
```

正常应至少有：

```dotenv
LOCAL_OCR_MODE=paddleocr
PARSER_API_KEY=...
```

## 20. 上线验收清单

部署完成后按以下顺序验收：

1. `docker compose ps` 所有默认服务正常；
2. `paddleocr` 为 `healthy`；
3. 浏览器能打开官网；
4. `/platform/login` 能登录；
5. `/workspace/login` 企业账号能登录；
6. 上传 TXT，文本解析正常；
7. 上传普通 PDF，原生文本解析正常；
8. 上传扫描 PDF，PaddleOCR 能识别；
9. 上传 JPG/PNG，PaddleOCR 能识别；
10. 上传 DOCX/XLSX/PPTX，能够转成可检索文本；
11. 文档 `chunk_count > 0`；
12. Embedding 成功写入 Qdrant；
13. RAG 能命中刚上传资料；
14. 低置信问题不会强行编答案；
15. 邮箱验证码可以发送；
16. 客服工单与人工接管可用；
17. 支付保持 sandbox，正式商户配置完成后再切生产；
18. 自动部署再次 Push 后能够完成更新。

## 22. 最终部署基准

当前正式私有化运行基准可以简单记成：

```text
GitHub main
+ docker-compose.private.yml
+ .env.private
+ knowflow-state
+ qdrant-data
+ paddleocr-cache
```

其中代码由 GitHub 管，密钥由 `.env.private` 管，业务状态由 Docker Volume 管。

这三类资产分开管理以后，Project4 的部署、升级、备份和交接会比旧版“仓库 + ZIP + 服务器手改代码”稳定很多。
